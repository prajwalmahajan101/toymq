## Problems I faced
**The unbounded-inflight bug was subtler than "no backpressure."** Delivery *did* have backpressure — `sendCh` (buf 64) + the socket TCP buffer — but only against a client that stops *reading*. The real gap was a client that reads eagerly and acks slowly: `sendCh` drains fast, `runDelivery` keeps producing, and `inflight` grows unbounded. The fix had to tie delivery rate to *ack* rate, not to socket readability — hence a credit window released by `Ack`, gated *before* the WAL read so the bound is `len(inflight) ≤ W`.

**Chose a wake channel over `sync.Cond`.** The gate must honour `ctx` cancellation (subscription teardown), and `sync.Cond` doesn't compose with `select`/`ctx`. A buffered-1 coalescing channel + a re-check loop closes the check-then-block gap: a signal arriving between the condition test and the blocking receive is retained and delivered next, so no wake-up is missed. Verified under `-race -count`.

**The window silently broke a pre-M5 test.** `TestThousandMsgPartialAckResumesAfterRestart` publishes 1000, subscribes, and receives all 1000 *before* acking — 500+ simultaneously unacked. With the default window it capped at 256 (`received 256 distinct MsgIDs, want 1000`). This was the window working correctly; the test's premise predates flow control. Fixed by routing the integration harness through `NewWithObservability` with a new `withRecvWindow` opt (generous 4096 default), which orphaned `NewWithTimingsPartitions` — removed it as dead code.

**Redelivery masqueraded as a window violation in the first test draft.** `TestReceiveWindowBoundsInflight` asserted "no MSG arrives" after receiving W, but got a redelivery of MsgID 0 — the 100ms visibility timeout resends the in-window inflight, which correctly bypasses the gate. The window bounds *distinct* inflight, not resends. Fixed by giving that test a long visibility (30s) so redelivery doesn't race the `expectNoMsg` grace windows.

**PAUSE has an at-most-one in-flight "slip."** PAUSE takes effect at the next `awaitCredit`; if the delivery goroutine is parked in `reader.Next` when PAUSE lands, the one record it's awaiting still delivers. The first client test tried to assert "no delivery while paused" and hung 600s — but the actual hang was self-inflicted: the test never acked, so redelivery re-pushed the messages forever and `drain`'s idle timer never fired. Fixed the test to ack-and-dedupe; made the *integration* pause test deterministic by using window=1 so the goroutine is parked in the gate (not mid-read), giving zero slip.

## What could have been done better
- I could have anticipated the redelivery/visibility interaction before writing the first window test — both flaky drafts (the 600s client hang and the redelivery false-positive) trace to not accounting for the redelivery ticker up front. Writing the "long visibility isolates first-delivery" assumption into the test *first* would have skipped two red-loops.
- The PAUSE slip semantics are correct but only got pinned down while debugging the hang; folding "how does PAUSE interact with a goroutine parked in `reader.Next`" into the brainstorm would have shaped the test design earlier.
