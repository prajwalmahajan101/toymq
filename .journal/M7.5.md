# M7.5 journal — Grafana LGTM stack (provisioned)

**Branch:** `feat/observability-stack` stacked on `feat/observability-m7`
**Goal:** Turn M7's emitted signals into a *pivotable* Grafana experience — logs ↔ traces ↔ metrics joined by `trace_id`, with SLO alerts pre-loaded. Config only; no Go code.
**ADRs:** decisions already recorded in [0027](../docs/adr/0027-correlated-telemetry.md) (LGTM + Alloy log path) and [0026](../docs/adr/0026-traceparent-wire-propagation.md).

## What I did
- **`docker-compose.observability.yml`** — separate from the metrics-only `docker-compose.yml` (left untouched). Full stack: `toymq --otlp→ otel-collector → tempo`; `prometheus` scrapes `:6790` with `--enable-feature=exemplar-storage`; `alloy` tails the toymq container's JSON stdout → `loki`; `grafana` ties all three together. Dev-grade single-binary Tempo/Loki/Alloy, ephemeral volumes.
- **Backend configs** under `observability/`: `otel-collector/config.yaml` (OTLP→Tempo), `tempo/tempo.yaml`, `loki/loki-config.yaml`, `alloy/config.alloy` (Docker log discovery → Loki).
- **Prometheus stack config** — `prometheus-stack.yml` (adds `rule_files`) + `alerts.yml` with **6 SLO rules** (WAL p99, redelivery, inflight backlog, publish-failure, consumer-lag, DLQ). Kept separate from the simple `prometheus.yml` so the metrics-only stack doesn't need the rule file mounted.
- **Grafana correlation** — a stack-only provisioning dir (`provisioning-stack/`) with all three datasources: Prometheus `exemplarTraceIdDestinations`→Tempo, Tempo `tracesToLogsV2`→Loki + `tracesToMetrics`→Prometheus, Loki derived field (`"trace_id":"(\w+)"`)→Tempo.
- **Dashboards** — kept the existing overview; added 3 consolidated boards (`toymq-broker`, `toymq-consumers`, `toymq-traces`) covering WAL/segments/retention/delayed/flow-control, lag/ack/nack/redelivery/DLQ, and an exemplar+logs correlation board. Generated as schema-39 JSON.
- **Docs** — README observability section: expanded metric table (★ M7 series), traceparent + LGTM-stack subsections, corrected the now-closed limitations.

## Problems I faced
**Two compose files, not one.** Adding Tempo/Loki/Alloy datasources or `rule_files` to the *existing* provisioning/prometheus config would break the simple `docker compose up` (missing services / unmounted rule file). Resolved by keeping the metrics-only stack pristine and shipping a parallel `docker-compose.observability.yml` + `provisioning-stack/` + `prometheus-stack.yml`. The overview dashboard JSON is shared between both (same mount path).

**Log→trace correlation without an OTLP log bridge.** Per ADR 0027 the broker logs JSON to stdout (no otel-log dep in the hot path). Alloy discovers the container over the mounted docker socket and ships raw lines to Loki; the *Grafana Loki datasource* does the `trace_id` extraction via a derived field, so the trace link is a query-time concern, not a shipping-time one.

**Verification without standing the whole stack up.** `docker compose config` validates the topology; `promtool check rules` (via the prom image, `--entrypoint promtool`) confirmed all 6 alerts parse; a name cross-check confirmed every dashboard/alert metric exists in `internal/metrics` (only `_bucket` differed — the histogram suffix). A full `up --build` smoke is the remaining manual step.

## What could have been done better
- The dashboards are consolidated (4 total vs the roadmap's 7) — denser boards, fewer files; noted so the roadmap's "7 dashboards" line is read as coverage, not file count.
- Didn't stand the full stack up end-to-end in this pass (7 containers + a Go image build); the static validation is strong but a live `up` would confirm the Alloy→Loki derived-field click-through visually.
