# v3 M1 journal — Raft embedding + single-node replicated path

**Branch:** `feat/toyraft-embed` (M1) → `chore/toyraft-rc3-bump` (rc.3 follow-up), both off `main`
**Goal:** `toymq --replicate` routes every mutating command through
`raft.Propose → StateMachine.Apply`; standalone mode byte-identical to v2. M1
owns determinism, apply-once, and crash-durability.
**Spec:** `docs/superpowers/specs/2026-09-09-v3-m1-raft-embedding-design.md` ·
**ADRs:** [0028](../docs/adr/0028-raft-embedding-command-envelope.md),
[0029](../docs/adr/0029-toyraft-rc3-propose-result.md) ·
**Dogfooding:** [`docs/TOYRAFT-MIGRATION-REPORT.md`](../docs/TOYRAFT-MIGRATION-REPORT.md)

## What I did

- **`internal/replication` package** — command `Envelope` + binary codec,
  `brokerSM` (`raft.StateMachine`), and a no-op single-node transport. Isolated
  so `raft` stays out of the broker core (a small `ApplySurface` interface the
  broker satisfies) and `broker` stays out of `replication` (no import cycle).
- **Broker seam split** — extracted the deterministic mutation tail
  (`applyPublish`/`applyAck`/`applyNack`/`createTopicLocal`) from the
  non-deterministic resolve (routing, clock). `AttachRaft` + a nil-check branch
  per mutating method routes through Propose→Apply when replicated, inline (v2
  bytes) when standalone.
- **`wal.Record.RaftIndex`** — append-only, written only when non-zero, so
  standalone records stay byte-identical to v2; the applied-index marker that
  makes restart replay idempotent.
- **cmd/config wiring** — `--replicate` / `--node-id` / `--raft-dir`; single-node
  assembly (filestorage + no-op transport + `Peers=[self]`, wait-for-leader).
- **rc.3 follow-up** — bumped `rc.2 → rc.3`, deleted the nonce registry (read the
  MsgID straight from `Propose`'s new result return), kept the `RaftIndex` guard
  and no-op transport (see below).
- **Tests (`-race`)** — determinism (two brokers, byte-identical WAL), apply-once
  / MsgID return, restart recovery (now full write-after-restart), standalone
  matrix unchanged.

## Problems I faced

**The whole M1 design hinged on `Propose` discarding the `Apply` result.**
`raft.Node.Propose` (rc.2) returned `(Index, Term, error)` and dropped Apply's
`any`, so a PUB's WAL-assigned MsgID had no way home. Built a nonce→channel
registry: the leader stamps a nonce, `Apply` resolves it, the handler reads it
after `Propose` returns (safe because `Propose` blocks until applied). rc.3
later returned the result directly, so the registry was deleted — but it was the
right call for rc.2.

**Neither shipped toyraft transport could build a single-node cluster.** `inproc`
needs a `Clock` typed against toyraft's `internal/clock` (unconstructable
externally); `http` rejects both an empty `PeerURLs` and self-in-`PeerURLs`, so
`peers=[self]` satisfies neither. Since a one-node cluster never Sends, a 4-line
no-op `raft.Transport` was the fix. rc.3 relaxed both, but the no-op stays as the
zero-dependency choice for N=1.

**Restart double-applied every message — the deep one.** rc.2 kept its applied
index in memory only and stubbed snapshots, so on restart it replayed the entire
committed log through `Apply`, while the broker WAL *also* recovered
independently → every message written twice (reproduced: partition head 5 vs 2).
The fix that matched the spec's "WAL = applied-state durability" model: stamp
each record with its raft `Index`, take the max on recovery as an applied
high-water, and skip re-applying any PUB at/below it. Sequential apply under
ordered fsync makes the global max a safe prefix high-water.

**But the idempotence guard couldn't restore write capability.** Even guarded,
rc.2 dropped every *new* `Propose` after restart — I traced it to `newNode`
constructing an empty in-memory log (`LastIndex()==0` while `commitIndex`
recovered), so a new append landed at index 1 ≤ commitIndex and was rejected.
That was a toyraft bug, not fixable from outside. So M1 shipped with
crash-durability *deferred* (idempotent-replay done, write-after-restart blocked)
— surfaced explicitly, not silently skipped — and I wrote the upstream findings
into the migration report.

**rc.3 closed all six findings.** toyraft restored the log on restart (B1), added
a durable applied-index checkpoint (B2), and returned the apply result from
`Propose` (F3), plus the transport fixes. Bumping made write-after-restart pass
(`TestReplicatedRestartRecovery` now asserts a post-restart publish gets the
correct next MsgID) and let me delete the nonce registry. The one thing that
*stayed*: the `RaftIndex` guard. B2's checkpoint only engages for a StateMachine
that implements `Snapshot`; `brokerSM` still stubs it (real broker-state
serialization is v4), so it opts into full-log replay and still needs the guard.
Easy to misread as dead code post-rc.3 — documented the constraint in ADR 0029.

## Outcome

Single-node `--replicate` serves PUB/SUB/ACK, survives restart with zero
duplication and full write capability, and leaves standalone mode untouched.
Determinism + apply-once + crash-durability green under `-race`; CI green;
merged. The mutual unblock closed: toymq's M1 dogfooding drove toyraft rc.3, and
rc.3 unblocks v3 M2 (multi-node kill-leader / partition-heal depends on B1).
Remaining v4 item: broker `Snapshot`/`Restore` to retire the `RaftIndex` guard
and gain log compaction.
